# PostgreSQL DDL

Target PostgreSQL 13+ unless the project pins an older version.

## Type mapping

| Logical type | PostgreSQL | Notes |
|---|---|---|
| short text | `varchar(n)` or `text` | `text` has no performance penalty; use `varchar(n)` only to enforce a real limit |
| long text | `text` | |
| case-insensitive text | `text` + unique index on `lower(col)` | `citext` needs an extension; the functional index is usually enough |
| integer | `integer` | |
| big integer | `bigint` | Default for surrogate keys |
| decimal / money | `numeric(12,2)` | Never `money`, never `float` |
| boolean | `boolean` | |
| date | `date` | |
| timestamp | `timestamptz` | Always; `timestamp` without zone loses information |
| time | `time` | |
| uuid | `uuid` | `gen_random_uuid()` is built in from PG 13 |
| json | `jsonb` | Indexable with GIN; `json` only to preserve key order |
| enum | `CREATE TYPE ... AS ENUM` or `CHECK` | See below |
| binary | `bytea` | |
| array | `text[]` | A real child table usually beats an array |

## Identity

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

Preferred over `bigserial`: standard SQL, and the sequence is owned by the
column. Use `GENERATED BY DEFAULT AS IDENTITY` when data loads must supply ids.

## Enumerations

```sql
-- Native type: fast, self-documenting; adding a value needs ALTER TYPE
CREATE TYPE order_status AS ENUM ('pending', 'confirmed', 'declined', 'cancelled');
ALTER TYPE order_status ADD VALUE 'refunded';   -- cannot run inside a transaction block

-- Portable alternative
status text NOT NULL CHECK (status IN ('pending', 'confirmed', 'declined'))
```

Renaming or removing an enum value is painful; prefer `CHECK` while the value
set is still moving, and a lookup table when values carry labels or ordering.

## Timestamps

```sql
created_at timestamptz NOT NULL DEFAULT now(),
updated_at timestamptz NOT NULL DEFAULT now()
```

PostgreSQL has **no** automatic `updated_at`. Add a trigger, or set the column in
the application - and say which you chose:

```sql
CREATE OR REPLACE FUNCTION set_updated_at() RETURNS trigger AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER orders_set_updated_at BEFORE UPDATE ON orders
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```

## Constraints and indexes

```sql
-- Name every constraint: the name is what appears in error messages and migrations
CONSTRAINT orders_customer_fk FOREIGN KEY (customer_id) REFERENCES customers (id) ON DELETE RESTRICT

-- Partial unique index: unique only among rows that are still active
CREATE UNIQUE INDEX customers_email_active_key ON customers (lower(email)) WHERE deleted_at IS NULL;

-- Expression and covering indexes
CREATE INDEX orders_recent_idx ON orders (customer_id, created_at DESC) INCLUDE (status);
```

Partial indexes make soft deletion workable, which is why the soft-deletion
question in `modeling-rules.md` matters here.

## Identifiers

- Unquoted identifiers fold to **lower case**. Use snake_case and never quote.
- 63-byte limit; long constraint names are silently truncated - name them explicitly.
- Reserved words to avoid as identifiers: `user`, `order`, `group`, `table`,
  `default`, `check`, `references`, `window`, `authorization`.
  `users` and `orders` (plural) are safe, which is one reason for plural tables.

## Canonical example

```sql
-- Derived from features/checkout.feature (REQ-1042, REQ-1043)
-- Assumptions: surrogate bigint identity keys; audit columns added; single currency per order.
CREATE TABLE products (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  sku         varchar(32)  NOT NULL,
  name        varchar(255) NOT NULL,
  price       numeric(12,2) NOT NULL CHECK (price >= 0),
  created_at  timestamptz  NOT NULL DEFAULT now(),
  updated_at  timestamptz  NOT NULL DEFAULT now(),
  CONSTRAINT products_sku_key UNIQUE (sku)
);

CREATE TABLE customers (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email       varchar(255) NOT NULL,
  created_at  timestamptz  NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX customers_email_key ON customers (lower(email));

CREATE TABLE orders (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id  bigint       NOT NULL,
  status       text         NOT NULL CHECK (status IN ('pending','confirmed','declined','cancelled')),
  total_amount numeric(12,2) NOT NULL CHECK (total_amount >= 0),
  currency     char(3)      NOT NULL DEFAULT 'JPY',
  placed_at    timestamptz  NOT NULL DEFAULT now(),
  CONSTRAINT orders_customer_fk FOREIGN KEY (customer_id) REFERENCES customers (id) ON DELETE RESTRICT
);

CREATE TABLE order_items (
  order_id   bigint        NOT NULL,
  product_id bigint        NOT NULL,
  quantity   integer       NOT NULL CHECK (quantity > 0),
  unit_price numeric(12,2) NOT NULL CHECK (unit_price >= 0),
  PRIMARY KEY (order_id, product_id),
  CONSTRAINT order_items_order_fk   FOREIGN KEY (order_id)   REFERENCES orders (id)   ON DELETE CASCADE,
  CONSTRAINT order_items_product_fk FOREIGN KEY (product_id) REFERENCES products (id) ON DELETE RESTRICT
);
```

The migration's reverse operation removes the four tables in the opposite order
(`order_items`, `orders`, `customers`, `products`) - write it out in the
`down`/rollback script, and never ship a migration without it.

## Pitfalls

- `timestamp` vs `timestamptz`: the former silently drops the zone. Use `timestamptz`.
- `numeric` without precision is arbitrary-precision and slower; always give `(p,s)` for money.
- `ALTER TYPE ... ADD VALUE` cannot run inside a transaction block, which breaks
  migration tools that wrap everything in one. Split that migration out.
- A `CHECK` cannot reference other rows. Aggregate rules ("at most 20 items in a
  cart") need a trigger or application logic - say so rather than pretending.
- `ON DELETE CASCADE` on a wide graph removes more than the user expects. Default
  to `RESTRICT`; use `CASCADE` only for true composition.
